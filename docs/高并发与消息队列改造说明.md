# NekoCafé 高并发改造 + 消息队列（RabbitMQ）说明

> 目标：高峰期支持 **1000 并发预约**，核心接口 **P95 ≤ 350 ms**；在合适的位置引入消息队列做**订单异步处理**。

---

## 1. 选型：为什么是 RabbitMQ 而不是 Kafka

| 维度 | 本场景诉求 | RabbitMQ | Kafka |
|---|---|---|---|
| 模型 | 订单副作用「任务队列」，逐条可靠处理 | ✅ 队列/路由/确认天然契合 | 偏日志流/事件溯源 |
| 死信 / 重试 | 失败要进 DLQ 人工兜底 | ✅ 原生 DLX/DLQ | 需自建 |
| 延迟消息 | 预约超时自动取消 | ✅ TTL + DLX 即可 | 需额外组件 |
| 吞吐量 | 千级并发、万级 TPS 足矣 | ✅ 够用 | 十万级才有优势 |
| 运维成本 | 学生/中小项目 | ✅ 单机即可、管理台友好 | 依赖 ZK/KRaft，重 |

**结论：RabbitMQ。** Kafka 的超高吞吐/持久化重放能力在本场景用不上，反而抬高复杂度。

## 2. 核心问题与对策

### 2.1 预约「检查-插入」竞态（会超卖 / 双重预约）
原 `createReservation` 用**非加锁 SELECT** 在 Java 内存里判断时段冲突，再插入——两个并发请求可能同时通过检查、同时插入，造成同一桌同一时段被订两次。

**对策（强一致，不能用最终一致）：**
- 按**桌位**加 **Redis 分布式锁**（`lock:table:{tableId}`，`SET NX PX` + Lua 比较删除），把「冲突检查 + 插入」串行化。
- 关键点：用 `TransactionTemplate` 把事务放在锁内，**锁在事务提交之后才释放**，确保后到的请求看到的是已提交数据（普通 `@Transactional` + 方法内释放锁会在提交前放锁，仍有竞态——本实现已规避）。
- 不同桌位用不同锁键，**互不阻塞**：1000 并发分散到多桌时吞吐不受影响。
- 索引 `idx_reservations_table_status` 让冲突检查走索引，缩短临界区。
- **DB 级强一致兜底（默认启用）**：`btree_gist` 时段排他约束（见 `mq_schema.sql` 第 4 节）。这是「绝不超卖」的最终防线——Redis 锁租约在高负载下可能在事务提交前过期，留下并发插入窗口；该约束由 DB 强制同桌时段永不重叠，无论锁是否抖动 / Redis 是否故障。命中冲突抛 `23P01`，代码已捕获转友好提示。注意：列为 `TIMESTAMP` 用 `tsrange`，`duration_min` 用 `COALESCE`；若历史数据已有重叠，`ADD CONSTRAINT` 会失败，需先按脚本注释里的排查 SQL 清理。
- 锁等待超时（同桌竞争激烈）抛 `IllegalStateException`，已捕获转 `code:503`「系统繁忙，请稍后重试」，不再冒泡成 `code:500`。

相关文件：`util/DistributedLock.java`、`service/impl/ReservationServiceImpl.java`、`mapper/ReservationsMapper.xml`（补 `useGeneratedKeys`）。

### 2.2 下单同步事务过长（拖垮 P95）
原 `submitOrder` 是一个巨型 `@Transactional`，串行执行约 10 次 DB 读写（改预约、占桌、核销券、**会员统计、积分流水、优惠券使用记录**、写菜品、写支付）。对远程 PostgreSQL 每次往返叠加，事务越长占用连接越久，1000 并发下连接池被吃满 → 排队 → P95 飙升。

**对策（瘦身 + 异步）：**
- **同步保留**（强一致 / 支付即时依赖）：改预约状态→CONFIRMED、乐观锁占桌、核销 `user_coupons`(防重复用券)、写 `order_items`、写 `payments`、写**发件箱**一行。
- **异步剥离**（最终一致即可）：会员累计金额/积分、积分流水、优惠券使用记录、门店新订单通知 → 通过 MQ 消费者处理。
- 净效果：关键路径减少 ~4 次 DB 往返，事务更短 → 连接更快归还 → 有效吞吐与 P95 同时改善。
- **状态护栏（幂等下单）**：`BOOKED→CONFIRMED` 改为条件更新 `WHERE status='BOOKED'`（`ReservationsMapper.confirmOrderIfBooked`）。`affected==0` 即拒绝，避免并发/双击重复下单写出重复 `order_items`/`payments`，也避免把「已被超时自动取消」的预约复活而占用可能已被他人预订的桌位。

### 2.3 双写问题（事务性发件箱 Outbox）
「DB 提交了但消息没发出」或「消息发了但 DB 回滚」会导致积分/通知丢失或幽灵消息。

**对策：本地消息表（Transactional Outbox）**
- 业务事务内把事件写入 `outbox_message`（与业务数据**同生共死**）。
- `OutboxPublisher` 定时（默认 500ms）`SELECT ... FOR UPDATE SKIP LOCKED` 取批，用 **publisher confirms**（`waitForConfirmsOrDie`）确认 Broker 收到后才标记 `SENT`；失败保持 `PENDING` 下轮重试 → **至少一次**投递。
- 多实例部署时 `SKIP LOCKED` 保证不重复投递。

相关文件：`mq/MessageOutbox.java`、`mq/OutboxPublisher.java`、`entity/OutboxMessage.java`、`mapper/OutboxMessageMapper.java`。

### 2.4 消费幂等 + 「取消 vs 异步」竞态
至少一次投递 → 消息可能重复消费；且用户可能在「异步加积分」之前就取消订单，导致回滚了根本没加的积分（积分变负）。

**对策：`mq_consumed` 原子抢占（一行定胜负）**
- `message_id = "ORDER_SE:" + reservationId`，`INSERT ... ON CONFLICT DO NOTHING` 抢占：
  - **消费者**用 `applied=TRUE` 抢占，且**抢占与副作用落库在同一事务**——`applied=TRUE` ⟺ 副作用已提交。
  - **取消订单**用 `applied=FALSE` 抢占（墓碑）：
    - 抢到 → 消费者还没结算、之后会跳过 → 本来没加，**不回滚**。
    - 抢不到且已有 `applied=TRUE` → 消费者已加 → **回滚**。
- PostgreSQL 对并发 `ON CONFLICT` 天然串行化，两条路径互斥，无论谁先到结果都正确。重复投递时消费者抢不到 → 安全跳过。

相关文件：`mapper/MqConsumedMapper.java`、`mq/consumer/OrderSideEffectConsumer.java`、`service/impl/OrderServiceImpl.java`（`cancelOrder` 已按抢占结果决定是否回滚）。

### 2.5 预约超时自动取消（延迟队列示范）
创建预约时往**延迟队列**（`x-message-ttl` + 死信转发）投一条消息；TTL 到期消息进入超时队列，消费者检查若仍为 `BOOKED`（一直没支付）则自动取消并释放桌位。延迟消息同样走发件箱可靠投递。

相关文件：`config/RabbitMQConfig.java`、`mq/consumer/ReservationTimeoutConsumer.java`。

## 3. MQ 拓扑

```
nekocafe.order.exchange (topic)
  ├─ rk=order.side-effect   → nekocafe.order.side-effect.queue   ──(重试耗尽)──┐
  └─ rk=order.notification  → nekocafe.order.notification.queue  ──(重试耗尽)──┤
                                                                              ▼
                                                              nekocafe.dlx (direct)
                                                                ├─ nekocafe.order.side-effect.dlq
                                                                └─ nekocafe.order.notification.dlq

nekocafe.reservation.delay.exchange → nekocafe.reservation.delay.queue (TTL=15min)
   --(到期死信)--> nekocafe.reservation.timeout.exchange → nekocafe.reservation.timeout.queue
```

消息体（JSON）见 `mq/event/OrderSideEffectMessage.java`、`mq/event/NotificationMessage.java`。

## 5. 性能预算（达成 1000 并发 / P95 ≤ 350ms 的依据）

1. **缩短关键路径**：下单减少约 4 次远程 DB 往返；按单次 RTT 10–20ms 估算，直接砍掉 40–80ms，且事务变短显著降低连接占用时间。
2. **连接池正确化**：HikariCP `maximum-pool-size=30`，`connection-timeout=3000`（拿不到连接快速失败而非线程堆积）。注意：远程**单实例** PostgreSQL 才是稳态吞吐的天花板，连接池不是越大越好（过大反而加剧 DB 上下文切换）。
3. **入口放量**：Tomcat `threads.max=400`、`accept-count=300`，承接 1000 并发瞬时连接。
4. **削峰**：突发流量先落 MQ，消费者按 `concurrency=4..16` 平滑消化，保护 DB。
5. **读热点缓存（后续可加）**：门店/菜单等高 QPS 读建议加 Redis 缓存，进一步降 P95（本次未改动业务读逻辑，留作下一步）。

> ⚠️ **诚实声明**：P95 ≤ 350ms 是**架构上可达成**的目标，但最终数值取决于**远程 PostgreSQL 的规格与网络 RTT**。必须用第 7 节的压测脚本在**贴近生产的环境（勿压生产库）**实测确认，并据结果回调连接池/线程数。本次交付保证：代码编译通过、MQ 链路可用、并发正确性（防超卖 + 幂等 + 不丢消息 + 取消不错乱）成立。

## 9. 风险与回滚
- **RabbitMQ 不可用**：下单/预约仍成功（发件箱已落库），消息积压在 `outbox_message=PENDING`，Broker 恢复后自动补投；副作用延迟到账，不丢。
- **消费者持续失败**：重试 4 次后进 DLQ，可在管理台排查/重放，不阻塞主流程。
- **回滚**：还原本次修改的文件即可；`outbox_message`/`mq_consumed` 表保留不影响旧逻辑。Redis 锁为加法增强，移除后退回原乐观锁行为（注意会恢复原竞态）。
